# Харнес, который вырос из багов: как Polemica Notes проверяет не только функции, но и архитектуру

Polemica Notes — открытое браузерное расширение для
[polemicagame.com](https://polemicagame.com). Оно добавляет заметки и статистику
игроков, игровые хоткеи, интеграцию с OBS и Twitch и собирается из одной
TypeScript-кодовой базы для Chrome и Firefox.

Весь код проекта открыт на GitHub:
[github.com/fjfalcon/polemica-notes](https://github.com/fjfalcon/polemica-notes).
Там же лежат все тесты, фикстуры и скрипты, упомянутые в статье.

На первый взгляд это небольшой пользовательский проект. Но у браузерного
расширения есть неприятное сочетание рисков:

- оно работает внутри постоянно меняющегося чужого сайта;
- несколько вкладок одновременно читают и меняют общее хранилище;
- service worker Manifest V3 может уснуть в середине сценария;
- ошибка в заметках способна затереть пользовательские данные;
- ошибка в DOM-обработчике может превратить одну мутацию в бесконечный цикл;
- Chrome и Firefox используют разные формы фонового процесса и дистрибутива.

Поэтому под «харнесом» здесь понимается не один test runner. Это весь контур,
который помещает production-код в контролируемую среду, проигрывает опасные
сценарии и не позволяет собрать релиз при нарушении включённых в gate
офлайн-проверок.

В версии 9.61.1 офлайн-набор содержит 1406 тестов в 87 файлах. Но главное не
количество. Главное — какие утверждения эти тесты делают исполняемыми.

## От памятки к исполняемому правилу

В проекте есть большой файл
[`AGENTS.md`](https://github.com/fjfalcon/polemica-notes/blob/main/AGENTS.md) с
архитектурой, картой хранилищ и правилами, появившимися после реальных сбоев.
Например:

- заметки должны жить в `storage.local`, а не в ограниченном `storage.sync`;
- записывать карту заметок целиком может только фоновый координатор и два
  явно рассмотренных fallback-пути;
- все DOM-подписчики должны сходиться к неподвижному состоянию;
- хоткеи обязаны учитывать раскладко-независимый `event.code`, ввод текста,
  модификаторы и `repeat`;
- при замене WebSocket нужно отвязать все четыре обработчика старого сокета;
- `enable()` и `disable()` должны быть симметричны по слушателям и таймерам;
- селекторы чужого сайта должны проходить через единый реестр.

Текстовое правило полезно, пока его помнят. Исполняемый инвариант полезен и в
пятницу вечером, и после большого рефакторинга. Поэтому значительная часть
харнеса занимается не проверкой результата отдельной функции, а поиском
архитектурно запрещённых состояний.

Общий контур выглядит так:

```text
чистая логика и state machines
              ↓
property-based и DOM-сценарии
              ↓
AST- и структурные инварианты
              ↓
fixpoint-харнес настоящего MutationObserver
              ↓
отдельный live-contract по требованию
              ↓
обязательный offline release gate и хэши артефактов
              ↓
процессный adversarial review изменений
```

Эти слои не заменяют друг друга. Каждый ловит свой класс ошибок.

## Первый слой: поведение, данные и конкуренция

Обычная офлайн-сюита запускается через Vitest:

```bash
npm test
```

Конфигурация явно включает
[`tests/unit`](https://github.com/fjfalcon/polemica-notes/tree/main/tests/unit)
и
[`tests/invariants`](https://github.com/fjfalcon/polemica-notes/tree/main/tests/invariants).
По умолчанию тесты работают в Node.js, а сценарии с DOM точечно переключаются
на jsdom.

Название `unit` здесь шире классического «одна функция, все зависимости
замоканы». В набор входят чистые функции, небольшие машины состояний,
DOM-интеграция и сценарии конкурентного доступа.

### Реальные данные вместо удобных предположений

Разбор матча проверяется на настоящих JSON-файлах. Это важно, потому что
предметная область содержит неочевидные правила. Например, записи голосования
без поля `num` — отдельный бюллетень «поднимаем всех?», а не голос за игрока
№1. При «попиле» покинуть стол могут несколько человек, поэтому результат дня
должен быть массивом, а не одним числом.

Production-логика находится в
[`match-outcome.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/src/content/match-outcome.ts),
а сценарии с реальными матчами — в
[`match-outcome.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/unit/match-outcome.test.ts).
Фикстуры также открыты: базовый
[`match_314446.json`](https://github.com/fjfalcon/polemica-notes/blob/main/legacy/match_314446.json)
и матч с попилом
[`match_598995.json`](https://github.com/fjfalcon/polemica-notes/blob/main/docs/fixtures/match_598995.json).

Такой тест фиксирует не только форму объекта, но и язык предметной области.
Это защищает от «логичного» рефакторинга, который на самом деле меняет правила
игры.

### Гонки моделируются как поведение

Заметки хранятся общей картой. Наивный сценарий выглядит так:

```text
вкладка A читает карту
вкладка B читает ту же карту
вкладка A добавляет Alice и пишет карту
вкладка B добавляет Bob и пишет свой снимок
изменение Alice потеряно
```

Поэтому вкладки отправляют в background не снимки, а намерения: изменить
конкретную запись или элемент палитры. Фоновый координатор последовательно
читает свежее состояние и применяет операции в одной очереди.

В
[`notes-coordinator.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/unit/notes-coordinator.test.ts)
проверяются потерянные обновления между вкладками, отказ чтения, граница
согласия при импорте и отсутствие параллельных критических секций. Отдельный
сценарий закрепляет важное решение: медленная задача должна удерживать очередь.
Таймаут, который отклоняет Promise, но не останавливает саму запись, только
создал бы иллюзию отмены и вернул параллельные изменения данных.

### Property-based тесты исследуют недоверенный ввод

Fast-check используется там, где пространство входов важнее набора ручных
примеров. В
[`notes-store.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/unit/notes-store.test.ts)
генерируются современные и legacy-записи, никнеймы и `u:<id>`-ключи. Проверки
закрепляют свойства слияния: идемпотентность, отсутствие новых ключей,
сохранение непустого текста и цвета.

В
[`page-storage-trust.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/unit/page-storage-trust.test.ts)
произвольные значения подаются в парсеры `localStorage` и `sessionStorage`
страницы. Это принципиальная граница доверия: хранилище принадлежит сайту, а не
расширению, поэтому даже корректный TypeScript-тип ничего не гарантирует во
время выполнения.

## Второй слой: архитектура как тестируемый контракт

Большой файл
[`architecture.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/invariants/architecture.test.ts)
читает production-исходники и проверяет устройство системы.

Для критичных утверждений используется TypeScript AST. Это результат
нескольких неудачных попыток решить задачу регулярными выражениями. Regex не
видел вызовы с generic-параметрами, путал объявление интерфейса с вызовом
функции и пропускал селектор, сохранённый в константе. Синтаксическое дерево
различает `CallExpression`, import alias, object literal и тело конкретной
функции по построению.

### Единственные писатели пользовательских данных

Инвариант обходит все TypeScript-файлы, находит импорты `saveNotes`, учитывает
алиасы и вызовы через внедрённую зависимость, после чего сравнивает результат с
точным allowlist. Новый вызов сохранения всей карты заметок в произвольной
фиче делает тест красным.

Так же охраняется палитра меток. Причина практическая: когда палитра ещё
сохранялась снимком из content-вкладки, две одновременные правки могли терять
друг друга, хотя заметки уже были защищены координатором.

### Селекторы чужого сайта

Разметка polemicagame.com — внешний API, только без версий и changelog. В
production есть реестр
[`selectors.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/src/core/selectors.ts).
Для DOM-запросов AST-инвариант ищет CSS-классы в строковых литералах и
шаблонных строках. Отдельно он контролирует строковые литералы, напрямую
переданные в `classList.*`; константы в таких вызовах остаются известной
границей. Новый класс сайта вне реестра требует либо перенести его в
`SITE`/`SITE_CLASS`, либо явно доказать, что это собственная разметка
расширения. CSS, завязанный на разметку сайта, контролируется отдельными
поимёнными списками файлов и классов.

Allowlist писателей данных, lifecycle и DOM enrollment намеренно точный. Он
хранит не просто имя файла, а ожидаемое количество исключений и причину. Если
исключение исчезло или в уже разрешённом файле появился ещё один опасный
вызов, тест тоже падает. Иначе allowlist быстро превращается в вечную дыру.

### Что ещё проверяют инварианты

В том же контуре закреплены:

- единственный `MutationObserver` на документ и его параметры;
- симметрия количества listeners и timers в feature-файлах;
- отсутствие `querySelectorAll("*")`;
- соответствие `Settings` и `DEFAULT_SETTINGS`;
- гейты центрального hotkey-роутера и blocker-а `role-faker`;
- наличие сброса четырёх WebSocket-обработчиков в OBS- и Twitch-клиентах;
- запрет секретов в вызовах логгера;
- соответствие permissions реальным `browser.*` API;
- соответствие версий package и base manifest;
- различия Chrome/Firefox manifest overlays;
- включённая минификация в конфигурации сборки и согласованность её описания.

Версию lock-файла отдельно проверяет релизный gate.

Это не статический анализ общего назначения. Это маленький проектный линтер,
который знает конкретные способы сломать именно Polemica Notes.

## Третий слой: DOM должен прийти к фикспоинту

Один из самых дорогих классов ошибок был связан с `MutationObserver`.
Расширение видит изменение страницы, обновляет собственный DOM, observer видит
это обновление и снова вызывает фичу. Если обработчик каждый раз пишет
`class`, `style` или пересоздаёт узел без проверки текущего состояния, цикл
поддерживает сам себя.

Обычный DOM-тест легко пропускает такой дефект:

```text
вызвали apply()
проверили, что карточка появилась
тест завершился
```

Но ошибка живёт на следующем обороте observer, который породила сама карточка.

### Настоящий конвейер вместо мока

[`dom-fixpoint.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/invariants/dom-fixpoint.test.ts)
принципиально не мокает production-модуль
[`core/dom.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/src/core/dom.ts).
В тесте работает настоящий jsdom `MutationObserver`, а мутации, созданные
фичей, возвращаются той же фиче.

Чтобы сделать процесс детерминированным, документ объявляется скрытым. В этом
режиме production-наблюдатель использует таймерный fallback вместо
`requestAnimationFrame`. Fake timers двигают время раундами по 600 мс:

```ts
for (let round = 1; round <= MAX_ROUNDS; round++) {
  const before = seen;
  await vi.advanceTimersByTimeAsync(600);
  await Promise.resolve();

  if (seen === before) quiet++;
  else quiet = 0;

  if (quiet >= 4) return { settled: true, rounds: round };
}
```

Четыре тихих раунда означают, что DOM достиг фикспоинта. Если изменения идут
все 60 раундов, тест сообщает о цикле подписчика.

Сценарии проверяют чужой профиль, собственный профиль, разлогин и совместную
работу двух профильных фич. Особенно важен собственный профиль: карточка
пересечений должна удалиться и больше не создаваться. Именно цикл
«вставка → самоудаление → новая мутация → вставка» когда-то прошёл мимо
ручной проверки.

### Канарейка проверяет сам харнес

Зелёный тест ещё не доказывает, что тест способен стать красным. Поэтому в
конце файла есть намеренно неидемпотентный подписчик:

```ts
const off = onDomChange(() => {
  document.body.appendChild(document.createElement("div"));
});
```

Харнес обязан классифицировать его как `settled: false`. Это негативная
канарейка: если кто-то сломает управление таймерами или перестанет возвращать
мутации в production observer, канарейка «позеленеет» не там, где нужно, и
уронит suite.

### Новая подписка не проходит незаметно

Поведенческий fixpoint-сценарий пока есть не для всех DOM-фич. Чтобы это
ограничение не расширялось молча,
[`dom-enrollment.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/invariants/dom-enrollment.test.ts)
находит текущие прямые вызовы `onDomChange(` в content-коде. Каждый файл должен
быть либо импортирован в fixpoint-харнес, либо находиться в точном
reviewed-списке с объяснением, почему его запись идемпотентна или почему
подписчик только читает DOM. Алиасы и обёртки остаются известной границей этого
статического сканера.

Это важная честность формулировки: харнес не доказывает сходимость всех фич.
Он полноценно проигрывает покрытые сценарии и заставляет явно рассмотреть все
остальные подписки.

В production есть и мягкий runtime-сторож. Если вне игровой комнаты DOM не
затихает больше минуты, он пишет одно предупреждение в лог. В самой комнате
такой сигнал отключён: активная игра легитимно создаёт постоянный поток
изменений, и универсальный детектор дал бы слишком много ложных срабатываний.

## Четвёртый слой: контракт с сайтом, которым проект не управляет

Даже идеальный код расширения перестанет работать, если сайт переименует
класс, изменит API или поменяет смысл CSS-состояния. Для этого существует
отдельный сетевой набор:

```bash
npm run test:contract
```

Он вынесен в собственную
[`vitest.contract.config.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/vitest.contract.config.ts),
работает последовательно и использует увеличенные таймауты.

### Не только «строка ещё встречается»

Первый вариант контракта проверял, что CSS-класс всё ещё присутствует в
бандлах сайта. Этого оказалось мало. Класс мог остаться, но начать означать
другое состояние.

Поэтому появились
[`semantic-probes.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/contract/semantic-probes.ts).
Они проверяют связи внутри свежих минифицированных бандлов:

- `cursor-pointer` по-прежнему связан с непринятой игрой;
- переход в комнату всё ещё создаёт POST-форму на `/game`;
- кнопка выхода ведёт через ожидаемую модалку и endpoint;
- признак выключенной камеры связан с доступностью видеотрека;
- обработчики остановки игры сохраняют ожидаемую матрицу действий;
- плитка игрока остаётся точкой отсчёта для абсолютных элементов;
- подписи фаз в RU-локали сохраняют ожидаемый смысл.

EN-локаль отдельно проверяется в
[`site-contract.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/contract/site-contract.test.ts)
той же production-функцией классификации фаз.

Пробы не выполняют скачанный JavaScript. Они используют стабильные строковые
якоря, точные регулярные выражения и строковые признаки. Часть сложных проб
ограничивает поиск окном вокруг якоря: две строки «где-то в бандле» ещё не
доказывают, что они относятся к одному обработчику.

### Для ключевых проб есть направленные мутации

Семантический контракт сам нуждается в проверке. В
[`semantic-probes.test.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/unit/semantic-probes.test.ts)
те же пробы запускаются офлайн на сохранённых фрагментах реальных бандлов, а
затем вход намеренно портится:

- POST заменяется на GET;
- endpoint выхода переименовывается;
- binding получает противоположный смысл;
- `position: relative` меняется на `position: static`;
- локализованная подпись заменяется другой.

Каждая перечисленная мутация обязана уронить целевую пробу. Это не полноценный
mutation-testing framework с общим score, а набор направленных мутантов для
самых опасных внешних контрактов.

### Сеть не должна притворяться изменением контракта

Общая обвязка
[`fetch.ts`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/contract/fetch.ts)
делает до трёх попыток, ограничивает восемью секундами ожидание ответа до
получения заголовков и повторяет запросы при сетевых ошибках и выбранных
транзиентных HTTP-статусах. Ошибки чтения тела и ответ `200`, который не
парсится как JSON, также считаются проблемой транспорта.

Транзиентная недоступность сайта приводит к `skip`, а содержательный drift — к
`fail`. Например, исчезнувший bundle с `404`, пропавший селектор или новая
форма API не маскируются под сетевой сбой.

Для JS- и locale-файлов с закреплённым полем `sha256` скачанные хэши
сравниваются с
[`site-contract.json`](https://github.com/fjfalcon/polemica-notes/blob/main/tests/fixtures/site-contract.json).
CSS проверяется семантически без закреплённого SHA. Новый хэш сам по себе
только предупреждает о пересборке сайта: минификация может изменить байты без
изменения поведения. После предупреждения всё равно выполняются
содержательные проверки. Обновить ожидаемые хэши можно только явной командой:

```bash
UPDATE_CONTRACT_FIXTURES=1 npm run test:contract
```

Получившийся diff фикстуры нужно прочитать, а не принять автоматически.

## Пятый слой: проверяется не только код, но и релизный артефакт

Даже зелёные тесты бесполезны, если в магазин отправился старый ZIP или
частично пересобранный Firefox-дистрибутив. Поэтому основной релизный сценарий
идёт через
[`release-assets.mjs`](https://github.com/fjfalcon/polemica-notes/blob/main/scripts/release-assets.mjs):

```bash
npm run release:assets
```

Полный прогон требует ключей AMO в окружении. Без них ZIP-файлы будут собраны,
но подпись XPI пропустится, а команда завершится с ошибкой.

Скрипт последовательно выполняет:

1. сверку версий в `package.json`, `package-lock.json` и base manifest;
2. production typecheck;
3. отдельный typecheck тестов;
4. всю офлайн-сюиту;
5. сборку Chrome и Firefox;
6. `web-ext lint` Firefox-дистрибутива;
7. упаковку ZIP;
8. запись штампа для ZIP и дерева Firefox;
9. подпись постоянного Firefox XPI через AMO и добавление его SHA-256 в штамп.

Live-contract сознательно не входит в обязательный релизный гейт: выпуск не
должен блокироваться из-за чужого downtime. Его запускают по требованию,
особенно при изменениях интеграции с сайтом.

### Штамп привязан к байтам

Файл `dist/.gate-stamp.json` содержит версию, Git HEAD, признак грязного
дерева, время сборки и SHA-256 артефактов. Для Firefox считается не только
хэш ZIP, но и дайджест всего дерева `dist/firefox`.

Реализация дайджеста находится в
[`dist-digest.mjs`](https://github.com/fjfalcon/polemica-notes/blob/main/scripts/dist-digest.mjs).
Пути сортируются, длины пути и содержимого входят во фрейм, а симлинк приводит
к отказу. Эти детали появились после adversarial review: простой конкатенации
путей и байтов недостаточно для однозначного дайджеста.

Перед публикацией
[`verify-dist.mjs`](https://github.com/fjfalcon/polemica-notes/blob/main/scripts/verify-dist.mjs)
пересчитывает хэши и проверяет Git HEAD. Поэтому команда частичной пересборки,
запущенная после гейта, инвалидирует штамп. Совпадающего номера версии уже
недостаточно: публикуются именно те байты, которые прошли проверенный прогон.

## Adversarial review как отдельный слой

После каждого изменения кода проект требует отдельный adversarial review.
Ревьюер получает diff и задачу не подтвердить решение, а атаковать его:

- найти пользовательский сценарий, который не был проигран;
- проверить потерю данных и гонки вкладок;
- проверить симметрию lifecycle;
- проверить Manifest V3 и различия браузеров;
- попробовать обойти новый инвариант;
- проверить, способен ли добавленный тест стать красным.

Находки исправляются, после чего тот же ревьюер проверяет обновлённый diff.
Раунды продолжаются до явного вердикта «К РЕЛИЗУ ГОТОВО».

История таких волн хранится в
[`review-ledger.md`](https://github.com/fjfalcon/polemica-notes/blob/main/docs/review-ledger.md).
Она показывает полезную особенность процесса: ревью находило ошибки не только
в production-коде, но и в самих исправлениях и тестовых стражах. Например,
regex-инвариант мог не видеть реальный вызов, снимок для отката брался уже
после изменения, а таймаут очереди создавал параллельные записи вместо защиты
от зависания.

Автоматизация здесь намеренно ограничена. `release:assets` предупреждает, если
текущая версия не упомянута в ledger, но не блокирует сборку. Скрипт не может
доказать, что ревью действительно было независимым и проверяло текущий diff.
Это остаётся дисциплиной разработки, а ledger — её механическим следом.

## Почему здесь нет browser E2E

В проекте нет Playwright- или Puppeteer-сценария с установленным расширением.
Это осознанное решение, а не забытый пункт.

Предлагавшийся smoke-тест выглядел разумно:

```text
загрузить unpacked extension
→ убедиться, что service worker жив
→ открыть popup
→ проверить, что content script внедрился
```

Но исторические production-проблемы были другими: конкретное значение в
storage у живого пользователя, гонка между вкладками, неверный route gate,
изменившийся смысл состояния сайта. Чистый браузерный профиль успешно прошёл
бы smoke и не заметил эти дефекты.

При этом постоянная стоимость E2E для соло-проекта велика: Chromium как
зависимость гейта, headless/GPU-флаки, поддержка авторизации и медиаразрешений,
реакция на каждое изменение разметки сайта. Уже существующие слои снижают риск
битой или устаревшей сборки через typecheck, manifest-инварианты,
`web-ext lint`, контракт и хэши артефактов.

У решения есть условие пересмотра. Первый реальный релиз, в котором bundle не
загрузится или popup не отрисуется, станет основанием добавить один узкий
browser smoke. Не десять E2E-сценариев, а минимальную проверку именно
подтверждённого класса отказа.

## Чего харнес не доказывает

Сильный контур полезен только при честно записанных границах.

- AST-стражи понимают выбранные синтаксические формы, но не являются
  полноценным data-flow-анализатором.
- Lifecycle-инвариант считает вызовы, но не доказывает совпадение target,
  callback и capture-флага.
- Fixpoint-харнес поведенчески покрывает две профильные фичи; остальные
  подписчики находятся в reviewed-реестре исключений.
- jsdom не воспроизводит остановку MV3 service worker, настоящий layout,
  медиаразрешения и все различия browser storage events.
- Live-contract может пропустить часть API-проверки, если сайт недоступен,
  требует авторизацию или временно не содержит подходящих данных.
- В проекте нет общего coverage threshold и автоматического mutation score.
- Настоящий OBS и полный игровой вечер всё ещё требуют ручной обкатки.

Именно поэтому контур состоит из разных доказательств, а не продаёт один
процент coverage как гарантию корректности.

## Что из этого можно перенести в другой проект

Самая переносимая идея — строить харнес вокруг дорогих способов отказа, а не
вокруг абстрактной пирамиды тестирования.

1. Записывайте инцидент как короткий архитектурный инвариант.
2. Выносите бизнес-семантику в чистую функцию и проверяйте её на реальных
   данных.
3. Для гонок моделируйте порядок событий, а не только итог одного вызова.
4. Критичные source-инварианты проверяйте через AST или поведение, а regex
   оставляйте детектором дыма.
5. Делайте allowlist точным: файл, количество исключений и причина.
6. Проверяйте сам тест негативной канарейкой или направленным мутантом.
7. Если зависите от чужого сайта, разделяйте сетевую недоступность и
   содержательный drift.
8. Привязывайте release stamp к Git revision и байтам артефакта.
9. Не добавляйте дорогой E2E «для галочки»; заранее сформулируйте класс
   отказа, который только он способен поймать.
10. Храните не только правила, но и историю причин. В Polemica Notes эту роль
    выполняют `AGENTS.md` и ledger adversarial-волн.

## Как запустить контур локально

Репозиторий можно клонировать и проверить обычными командами:

```bash
git clone https://github.com/fjfalcon/polemica-notes.git
cd polemica-notes
npm install

npm run typecheck
npx tsc --noEmit -p tests/tsconfig.json
npm test
npm run test:contract
npm run build
npm run lint:ext:firefox
```

Состав команд и зависимости видны в
[`package.json`](https://github.com/fjfalcon/polemica-notes/blob/main/package.json),
а актуальная структура проекта — в
[`README.md`](https://github.com/fjfalcon/polemica-notes/blob/main/README.md).

## Вместо вывода

Харнес Polemica Notes не проектировался целиком заранее. Он вырос из потерь
данных, DOM-циклов, смены контрактов сайта, ошибок сборки и находок независимых
ревьюеров. В этом его практическая ценность: каждая заметная часть контура
отвечает на вопрос «какой уже известный способ сломать продукт больше не
должен пройти молча?».

Unit-тесты отвечают за локальную семантику. Property-based проверки исследуют
недоверенный ввод. State-machine сценарии воспроизводят гонки и жизненный
цикл. AST-инварианты охраняют архитектуру. Fixpoint-харнес доигрывает
DOM-мутации, которые породил сам production-код. Live-contract следит за
чужим сайтом. Release stamp связывает зелёный прогон с конкретными байтами.
Adversarial review пытается найти то, о чём все предыдущие слои ещё не знают.

По отдельности ни один из них не даёт полной гарантии. Вместе они превращают
накопленный опыт проекта из памятки в работающую систему обратной связи.
